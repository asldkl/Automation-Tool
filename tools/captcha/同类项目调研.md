# 「包含文字」类验证码 · 同类项目调研与可落地方案（2026-09-21）

> 背景：本地字形模板匹配已上线（门控自动提交 22/25、精度 100%），但两个短板没解决：
> ① 跨图分数不可比 → 只能靠门控保守提交；② **不知道要选几张（k 未知）**。
> 本文件汇总 GitHub 同类项目的做法、可行性评估，以及两个本地实验的（诚实）结果。

## 一、同类项目在怎么做

| 项目 | 机制 | 其自述成绩 | 关键可借鉴点 |
|---|---|---|---|
| [MgArcher/Text_select_captcha](https://github.com/MgArcher/Text_select_captcha)（及 lovelydengxia / zxinED 等 fork） | **YOLOv5 定位 + Siamese 孪生网络字形匹配**（不做 OCR） | 96% 准确率、100~300ms、**300 张就能训**、CPU 可跑（1 核 2G） | ① 两段式：先「找字块」，再「比字形」；② **k 由逐块分类结果自动得出**，不靠阈值；③ 提醒「直接上 OCR 往往不到 70%」 |
| [nickliqian/darknet_captcha](https://github.com/nickliqian/darknet_captcha) | darknet/YOLO3 目标检测，单分类或多分类点选 | — | 多分类点选 = 每块一个类别 → 需要点几个是**数出来的** |
| [xf867/captcha-ai-solver](https://github.com/xf867/captcha-ai-solver) | 大模型做语义理解 + OpenCV 定位，覆盖滑块/点选多类 | 92%+ | 「提示语解析」单独作为一层；语义类点选可零样本 |
| [OFA-Sys/Chinese-CLIP](https://github.com/OFA-Sys/Chinese-CLIP) | 中文图文对比学习（2 亿图文对），**支持导出 ONNX/TensorRT** | 中文检索 SOTA，零样本分类可用 | 零样本「这张图对应哪个字」；量化后图像编码器 84MB、文本编码器 197MB |
| 天翼云/百度等技术综述 | 流水线：图像采集 → 预处理 → 推理引擎 → **决策逻辑** → 模拟点击 | — | 明确把「决策逻辑层」单列：**把模型输出转成点击序列**是独立一环 |

**共同点（也是最重要的结论）**：主流做法都**不是**给每块算一个"像不像"的分再切阈值，
而是让每块**独立回答"我是什么字 / 我是不是目标类"**，于是 k = 判为目标类的块数，**自然得出**。
我们现在的短板恰好就在这一步。

## 二、我们的情况与它们的差异

| 维度 | 经典文字点选 | 我们这类 |
|---|---|---|
| 图块定位 | 需要检测（YOLO/darknet） | **不需要**：固定 6 格网格，`detect_image_tiles` 已稳定检出 |
| 题面 | 顶部提示框里给出目标字（可数出 k） | OCR 从题面读目标字（14/14 正确）→ **k 只能靠图块判定**，题面不告诉 |
| 字形来源 | 渲染字体/手写，检测+匹配即可 | **字由风景纹理拼出**（绿树/山脊/雪坡），干扰块是**形近的别的字** |
| 可比性 | 同类渲染字之间比 → 阈值可移植 | 纹理图块之间比 → **分数跨图不可比 → 全局阈值不存在**（已验证几何上无解） |

→ 也就是说：**"定位"这一环我们省掉了，难点全部压在"逐块身份判定"上。**

## 三、本轮做的两个实验（含一个失败）

### ❌ 实验 1：零训练「词表最近邻」逐块分类 → 证伪
思路：渲染 GB2312 一级字库（实测 6763 字）× 2 字体 → blackhat 响应 → bbox 归一化 → 40×40 描述子；
图块同样处理 → 余弦最近邻 → 选中集 = {预测为目标字的块}（k 自动得出）。

结果（`tools/captcha/exp_vocab_nn.py`，25 张 / 150 块）：
```
逐块分类（词表最近邻，零训练）：全对 0/25   逐块 精度 0% / 召回 0%
对照 · 现有生产档位（阈值 0.40 直接判定）：全对 23/25 = 92%
```
诊断：150 块预测出 **113 个不同字**（描述子不是坏的），但**目标字一次都没进过 argmax**，
余弦全挤在 0.18~0.44（均值 0.305）。原因很具体：
- 图块 140×140 里字只占一部分、笔画细 → 降到 **40×40 后细笔画被抹平**；
- 而渲染字是**字占满整幅** → 两者尺度根本不可比；纹理图上"取最亮 10% 像素估笔画 bbox"也不可靠（几乎取到整幅）。
→ **零训练的全局描述子这条路走不通。要做逐块分类，必须(a)在已定位的局部比较，或(b)用学习到的表示。**

### 🔜 实验 2（未做）：零样本 CLIP
把每块图 + 文本「一个写着『忠』字的图」送入中文 CLIP → 比相似度。
优点：**跨块/跨图可比性好**（语言监督自带校准），零训练、可直接在 25 张上试。
成本：需下载权重（图像编码器 ONNX 约 84MB 量化版，可外置，与 `best.onnx` 同模式）。
风险：CLIP 学的是"自然图像 + 真实文字"，我们这类"纹理拼字"域差未知 → **建议先小规模试，别先下结论**。

## 四、「不知道要选几张」的三条出路（按性价比排序）

### 🥇 C. 用游戏本身当 oracle（不需要任何模型，今天就能做）
提交流程改成「提交 → 复核 → 不通过则递减 k 重试」：
1. 门控通过 → 点选 + 确认；
2. **复核**：重新 OCR 识别区域，若题面还在 → 说明没过；
3. 没过则把选中集**按分数从低到高砍掉 1 块**（或直接点「换一组」）再试一次。
依据：现有 `conf` 已经把"该不该提交"分得很准；错例（`测试/34 (2)`、`测试1/35`）都是**多选了一块**，
砍掉最低分那块就正好对。预期把 22/25 的一次成功率变成"两次内几乎必中"。
⚠️ 需确认：游戏允许多少次重试、是否会锁号。

### 🥈 A. 训一个「逐块验证器」（本机已具备条件）
- 本机 **torch 2.13(CPU) + ultralytics 8.4 都在**；打包 spec 排除 torch，但可**导出 ONNX 外置加载**
  —— 与滑块 `best.onnx` 完全同模式（用户目录 + 设置界面导入）。
- 样本构造：正例 = 真实图块（已知答案块）+ 渲染字；负例 = 干扰图块 + 其它字渲染；
  可用 `sample_collector` 把样本从 150 块扩到几千块（**这是它第一次真正派上用场**）。
- 目标不是"认字"，而是学出一个**跨图可比的二值判据**（这正是手写算子的死穴）。
- 风险：图块样本增长慢；合成数据的域差需要验证。

### 🥉 B. 零样本 CLIP（先小规模验证再决定）
见「实验 2」。若 25 张上能到 ~80% 逐块准确，就值得认真做（零样本、无需标注、跨图可比）。

## 五、建议的下一步

1. **先做 C**：改动小、无外部依赖，能把现有 22/25 直接变成"两次内更高"。需要你确认重试代价。
2. **并行做 A 的数据准备**：用样本采集器批量攒"图块 + 答案"（现在只有 25 张/150 块，训不了任何模型）。
3. **B 作为可选探索**：要不要下 CLIP 权重先试一把，等你点头（84MB 外置，不影响打包体积）。

## 附：与现有代码的衔接点

- 复核复用 `captcha_router.gather_region_text()`（已在用），判断题面是否还在。
- 重试复用 `captcha_router.route_and_solve` 的刷新预算与 `refresh_available()`。
- 砍 k 重试只需在 `captcha_glyph_flow.solve_glyph_captcha()` 里多带一个「排除集」参数。
